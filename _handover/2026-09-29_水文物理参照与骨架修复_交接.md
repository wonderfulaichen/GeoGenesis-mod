## 2. 参照探针架构（新对话直接复用）

**文件**：`src/diagnostics/java/com/geogenesis/worldgen/hydrology/HydroRefProbe.java`

**运行**：
```bash
gradlew runHydroRefProbe '-PprobeArgs=seed bx bz radius margin samples streamFrac'
# 例：'-PprobeArgs=9139912035078620160 -140 137 700 192 8000000 0.005'
```
参数：`margin`=192（块）、`samples`=8,000,000、`streamFrac`=0.005（成河阈值=上游面积占比）。

**流水线**：
1. **① 采样** `gen.erodedHeightForRouting(wx,wz)`，1 块分辨率，窗口+margin（N=1785）。
   > 刻意不建 `GeoGenesisTerrain` / `RiverLineNetwork`（参照必须与现有水文独立）。
2. **② priority-flood 填洼**（Barnes 变体，`FILL_EPS=1e-5`）：用途①速度场（让粒子穿过洼地走到海）；
   用途②湖层（`fill − h > 0.5` = 洼地蓄水，用户定义）。
3. **③ 速度场 `v = −∇h`**（移植 `geotransport-main/source/geotransport/gradient.cu`）：
   中心差分，边界退化为单侧；**必须在 double 上求差分再转 float**（ε 梯度 1e-5，float(~100) 会吞掉）。
4. **④ 蒙特卡洛流线积分**（移植 `path.cu::__solve_uniform`）：
   粒子起点连续均匀随机 → 双线性采样速度 → **格心穿越步长 `__stepsize`**（0.5·(tx+tz)，上限 √2）
   → 每进入新格累积一次；并行（每线程独立 RNG 流 + 独立计数，按线程号升序汇总 ⇒ 仍逐位确定）。
   **动量滤波**（来自 SimpleHydrology）：`dir = normalize(0.85·dir + 0.15·v̂)`。
5. **⑤ 图层**：湖 = `fill−h>0.5`；河 = 追踪折线。
6. **⑤b–e 生命周期追踪**：
   - 湖编号 + 每湖主入流口（最大 acc 格）；
   - `next[]` 流向图（速度方向；平坦退化 fill 面 D8）→ **只用于逆流回溯与算溢口**；
   - 每湖溢口 = 从主入流口沿 `next[]` 走到离湖的第一个非湖格（priority-flood 最低通道）；
   - 源头 = 成河格中河格入度为 0 者，**逆流回溯**到分水岭真源头；
   - 顺流追踪用**动量粒子连续积分**（非 `next[]`）；入湖断段 → 跳到该湖溢口接续 → 入海终止。
7. **⑥ 出图**：`shade()` 与生产探针 `WaterViewProbe.shadeGray` 同口径
   （标准 Lambert：法线归一化 + NW 光源 `(-0.5,0.7,0.51)`，`60+175·max(0,d)`，1 块分辨率求梯度）。

**渲染约定**：粗 2px 亮青 `0x00E5D0` = 成河段；细 1px 暗青 `0x2E8B8B` = 源头细流；
白点 = 湖溢口；蓝 `0x4A90E2` = 湖；深蓝 `0x1F4E79` = 海。

## 4. 踩坑清单（新对话务必先看，勿重犯）

1. **不要用逐格方向图（`next[]`）正向追踪画河** → 平原 ε 阶梯会出"电路板"式直角折线。
   正向追踪必须与 MC 粒子同款（动量连续积分）。
2. **不要每源头各画一条完整轨迹而不合并** → 下游主干被叠画成"多股平行束"。
   必须：源头按 acc 降序 + 5×5 邻域并入检测 + 全局已画标记。
3. **不要把速度场建在 float 上求差分** → ε 梯度被浮点分辨率吞掉。
4. **不要单看水深判湖/河**：Manning 导水率 ∝ D^1.67 + 出流限幅 ⇒ 大流量格必然深（大江被判成湖）；
   反过来"先判河"又让深湖内被放大的通量涂成青色。正解 = **地形洼地测试**（湖）+ 流量（河）。
5. **不要用"阈值提取 + 骨架化"代替物理** → 用户明确驳回（那是被校验对象本身）。
6. **不要给参照湖加面积/深度门槛** → 用户明确驳回两次（"明明湖泊就是水在洼地堆积"）。
7. **参照图阴影必须 `shadeGray` 同口径** → 曾因自创 `200−v*900` 被指出"和游戏不一样"。
8. **参照地形必须用雕刻前**（水文输入），否则循环论证；游戏图是雕刻后 —— 这是**必然差异**，非 bug。
9. `build.gradle` 的 `runWaterViewProbe` 堆必须 ≥5g（eroded 模式 2g 会 OOM）。

### 10.3 用户实机"河像方块拼起来 / 河太多"→ 三处根因（已修，待复验）

**A. 方块感（三处）**
1. **水面 = 本格地形高度** ⇒ 沿河逐格锯齿 ⇒ 灌水判定逐格翻转 ⇒ 水一格有一格无。
   修：**单调水面剖面** `s = min(fill, max(h, s[下游]))`，按 fill 降序传递
   ⇒ 构造上沿程只降不升、恒在 [地形, 填洼面] 之间（`HydroTileBalance.monotoneRiverSurfaces`）。
2. **段内恒定**（宽度/深度/水面每 4 块才变一次）。修：采样端**两端插值**（按投影参数 t）
   + 河宽基准 W0 1.5→2.5。
3. **中心线锁死在格心**（±45° 折线）。修：**沿真实最陡下降的连续流线**
   （中心差分梯度 + 闭式格间步长 + 拓扑护栏；`HydroFlowGeometry.buildPolyline`）。
4. 并把 **`CELL_BLOCKS` 4 → 2**（台阶间距与量化幅度双双减半；4 块格是方块感的结构来源）。
   实测（玩家视角出图）：干河槽 268→**0**、计划下切最小 0.22→**0.92 块**、链长 33→**73 格**。

**B. "河太多"（一处）**：**成河门槛的物理量太小**。
- `channelThreshold = 120 块²` ≈ 11×11 块集水就成河；现实"河道起始集水面积"是
  **10⁴~10⁶ 块²**（0.01~1 km²）⇒ 差 2~4 个数量级 ⇒ 几乎每条坡面都长出"河"。
- 实测标定（`runHydroCarveDecisionProbe` 新增 [选档] 段，一次解析出全候选）：
  | 阈值 | 河格占比 | 河头/10⁶块² | 平均半宽 |
  |---|---|---|---|
  | 120（旧） | 7.01% | **643** | 7.6 块 |
  | 800 | 3.52% | 288 | 10.4 |
  | 1500 | 2.26% | 166 | 12.0 |
  | **3000（新）** | **1.02%** | **91** | 14.2 |
  | 6000 | 0.13% | 15 | 17.0 |
  现实参照：河头 1~100 个/10⁶块²、河格 0.3~3% ⇒ 取 **3000**；
  `widthAreaRef` 同步挂到阈值（河头才是小沟、下游才变宽），W0=2.5。
- 实测（r=192）：源头 86→**16**、链长 33→**105 格**、河宽按流量分层（河头 1.5 块 → 干流 20+ 块）。

`scaleBlockPos=1`/`renderScale=1` 为原值。用户感到"分辨率变粗"的真因是 A 的**产出量化**（已修）。

**探针解耦（防假失败）**：`HydroCoreProbe`/`HydroLifecycleProbe` 里写死的"块"常量

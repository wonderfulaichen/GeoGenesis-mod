## 修复 PreviewWorker Cell 网格采样粒度错误

**根因**：`PreviewWorker.compute()` 第 148 行调用 `terrain.getRegionCells(originX, originZ, texW, texH)`，其中 `texW/texH` 为纹理像素数（256×171），但 `getRegionCells` 按 block 粒度采样 `cellCountX×cellCountZ` 个连续 block。导致采样 256×256=65,536 个冗余 block（全部集中在 origin~origin+255 狭窄范围），而非视口覆盖的数千 block 范围。

**修复三处**：
1. **采样粒度**：用 `terrain.sampleCell(wx, wz)` 在视口真实世界坐标位置（间距 `pixelToWorldScale` blocks/pixel）采样，数量 = `sampleW × sampleH`（stride 分辨率）
2. **世界坐标映射**：`fillLayerPixels` 将像素坐标转换为真实世界坐标传递给 `GeoPalette.color(worldX, worldZ, ...)`，之前传的是像素坐标 `gx, gz`（0~255），导致 LATITUDE 图层纬度计算完全错误
3. **网格尺寸自适应**：`computeLayer` 检测 grid 与纹理尺寸的步长比（`gridStride`），支持 stride 分辨率网格（QUARTER 阶段）和全分辨率网格（FULL 阶段）统一处理

**编译**：BUILD SUCCESSFUL in 17s

## 修复预览仍不显示（性能根本问题）

**用户报告**：截图中预览区始终显示"计算中..."，legend 已绘出（说明 MC 端 UI 在更新）但中心区域无图像。
**日志检查**：`run\logs\latest.log` 中无任何 `Exception`/`at com.geogenesis` 记录 → 非崩溃，是 Worker 一直在跑。
**截图参数**：scale=6.0, texW=256, 默认宽 ~400 → `pixelToWorldScale ≈ 9.4 blocks/pixel`。
**视口覆盖** = 256*9.4 × 171*9.4 = **2406×1607 块 = 151×101 = 15,251 个 chunk**。

**真正的瓶颈（不是采样）**：
- `GeoGenesisTerrain.CACHE_SIZE = 256`，而预览需 15,251 个 chunk
- `pruneIfNeeded` 每次超过 256 删 **1/2**（128 个）→ 缓存剧烈抖动
- QUARTER 采 2,688 个位置覆盖 15,000 chunk → 15,000 个新 chunk 反复生成/淘汰
- 每次 chunk 生成 = 256 格 CellGenerator.sample() 含 Voronoi+多噪声 → ~25-50ms/chunk
- 实际总耗时 = 15,000 chunk × 50ms = **12+ 分钟**，且 FULL 相位再次从头重做
- 但 `RiverField.apply()` 在 generateChunk() 中**被注释掉**，所以 `cell.riverNetDist=1.0`（默认值）→ 即使渲染出来 RIVER_NETWORK 图层永远是黑色

**修复（4 处）**：
1. `GeoGenesisTerrain.CACHE_SIZE: 256 → 4096`（16× 容量，~50MB 内存，16,384 cell 缓存）
2. `pruneIfNeeded` 淘汰 1/2 → 1/8（避免误删最近使用 chunk）
3. `PreviewWorker.setPixelToWorldScale` 夹到 ≤ 4.0 blocks/pixel
   - cap=4 视口 = 1024×683 块 = 64×43 = 2,752 chunk（在 4096 缓存内秒级）
   - 超 cap 自动缩小显示区到 1024 块宽（用户仍可拖动看其他区域）
4. （隐含）`queueProgressive` 的 FULL 相位现在只是缓存命中，不重算

**编译**：BUILD SUCCESSFUL in 16s

**后续待优化**（非阻塞）：
- `CellGenerator.sample()` 中 `VoronoiRegionField.sampleBlend` 是热点，profile 后可能优化 2-3×
- `riverField.apply()` 是注释掉的，重新启用需 ~3 倍 chunk 生成时间
- 用 `LinkedHashMap accessOrder=true` 替换 ConcurrentHashMap 做真 LRU

## 修复预览不显示（动态 stride + 取消 computing 阻塞）

**核心问题**（参考 World-Preview-TFC 对比发现）：
1. **all-or-nothing 模式**：必须所有采样完成才回调显示，无一像素显示前永远是"计算中..."
2. **stride 固定 16 不够**：MC 预览（cap=4）需 160 个 chunk × ~50ms = 8-30 秒
3. **`computing=true` 阻塞后续请求**：compute 期间用户拖动无效
4. **`computeLayer` 里 `catch (Exception ignored)` 吞异常**：任何 RuntimeException 导致 onComplete 永不触发

**修复**：
1. **动态 stride**（PreviewWorker.TARGET_SAMPLES = 32）：`stride = ceil(sqrt(texW*texH/32))`，MC 预览 → 6×4=24 采样，独立窗口 → 8×8=64 采样
2. **取消 computing 阻塞**：`requestResample()` 删掉 `if (computing) return;`，改为始终 `worker.cancel()` 再调度新任务
3. **`computeLayer` 异常处理修复**：`catch (Exception ignored)` → `catch (Throwable t) { t.printStackTrace(); onComplete.accept(cache); }`
4. **computeLayer 支持 stride > 1**：用 upsampleNearest 替代 fillLayerPixels 满分辨率填充
5. **去除 Resolution.stride 固定值**：改为从动态 stride 计算，Resolution 枚举只作相位标识

**编译**：BUILD SUCCESSFUL in 18s

## 真正的根因：色带最低端与背景几乎同色（2026-07-22 第三轮）

**用户日志反馈**：`first 4 pixels = 0x1a1c24 0x1a1c24 0x1a1c24 0x1a1c24`
- 0x1a1c24 = RGB(26, 28, 36) = S_RIVER_NETWORK 0.0 停靠点
- 背景色 0xFF101418 = RGB(16, 20, 24)
- **ΔR=10, ΔG=8, ΔB=12** —— 几乎完全同色！

**根因诊断**：
1. ✅ 纹理**确实**已成功上传（hasTexture=true, done=true, blit 已执行）
2. ❌ 色带最暗端（深海/无河区）RGB ≈ (7,22,54) for ELEVATION, (16,17,20) for RIVER_NETWORK
3. ❌ 背景色 0x101418 也是相近的深灰
4. 采样只有 5×5=25 点，对于 RIVER_NETWORK 几乎不可能采到河流附近 → 全部像素都是 0.0 底色

**修复**（四件事）：
1. **改背景色** 0xFF101418 → 0xFF1a1a2a（蓝灰深色，与海洋色明显区分）
2. **提高 TARGET_SAMPLES** 32 → 144（12×12，详细 4.5 倍）

4. **S_RIVER_NETWORK 最暗端** RGB(16,17,20) → RGB(77,82,92) — 明显浅灰

## 修复：渲染框 vs widget 框不对应（2026-07-22 第四轮）

**用户截图反馈**：看到的是 24×24 地形图，但**只占 widget 中间一小块**，外面是大片深色背景（用户用红圈标出）。

**根因**：我前一轮重构 `uploadFromCache`（直接写 NativeImage 简化方案）时**误删了更新 `texScale` / `texOriginBlockX/Z` 的几行**！

旧逻辑（被删）：`uploadFromCache` 末尾会更新
```java
texOriginBlockX = originBlockX;
texOriginBlockZ = originBlockZ;
texScale = (double) width * scale / texW;  // ← 关键
```

新逻辑（缺）：只 `texture.upload()`，texScale 保持字段初值 `6.0`

**数学推演**：
- widget 宽 587，scale=6.0，texW=256
- 应有：`texScale = 587 * 6 / 256 = 13.76` → `drawW = 256 * 13.76 / 6 = 587`（覆盖全宽）✓
- 实际：`texScale = 6.0`（字段默认值）→ `drawW = 256 * 6 / 6 = 256`（仅 1/2.3 宽度）✗

**修复**：恢复 `uploadFromCache` 末尾更新这三个字段。同时**取消 cap 4.0**：
- worker 端 `pixelToWorldScale = min(s, 4.0)` 是为了控制采样工作量（避免生成太多 chunk）
- display 端 `texScale` 只是渲染数学（blit 拉伸），不应被 worker cap 限制
- 即使 worker 只采了 1024 blocks 范围的细节，texScale 仍按 13.76 算 → 纹理被拉伸覆盖整个 widget

**编译**：BUILD SUCCESSFUL in 13s

**经验教训**：
- 简化代码时**所有副作用都要迁移**，不能只搬主要逻辑
- 涉及到"位置/缩放/视口"映射的代码块，**保留映射基准的更新**
- display 端数学 ≠ worker 端 cap，要分开处理

# 水文统一水面方案（2026-10-05）

> **本文档的位置**：这是五次修复失败后的重思考。基于对三个参考项目的实证调研，
> 提出水文模型核心矛盾的解法。**未经用户批准不动代码。**

---

## 一、为什么五修全部失败（根因总结）

五次修复（BFS入湖口→最低鞍口→head-start→壅水过堰→水位合并）的共同盲点：
**都在修"出口怎么找/水怎么注入"，但真正的病根是模型里有两套互相打架的水面。**

| 水面 | 来源 | 性质 |
|---|---|---|
| `EquilibriumWater.level` | minimax 洪泛（几何） | "水刚好能溢出的高度"，湖内被抹平 |
| `LakeWaterBalance.level` | 水量平衡（来水=蒸发） | 被**钳在鞍口 -1e-9** |

矛盾的必然产物（全部实测）：
1. 湖内 parent 大量 = -1（minimax 抹平）⇒ 流线靠 parent 逃生失败
2. 溢口外那格 bed 比水面高 0.08 块 ⇒ 永远干燥 ⇒ 水物理上出不去
3. 注入流线被推回湖（lakeStill 85%）
4. 我合并两套水面后，湖面全平 ⇒ ∇=0 ⇒ 流线更死（failNoParent 5.8万→27.6万）

## 二、三个参考项目的实证结论

| 项目 | 有水面？ | 对我们的价值 |
|---|---|---|
| **SimpleHydrology** | ❌ 无 | **反证**：它的 priority-flood 洪泛被作者实测"buggy + slow"后**整体删除**（README:70-72, 2023-01）。我们正在用同类算法。 |
| **geotransport** | ❌ 无 | **反证**：作者自认"pits basically don't really go away"（path.cu:94-98）。水深参与流速的代码 `flow_steady` **唯一调用点被注释掉**——即"水深接进流动"这条路他们也没走通。 |
| **FreeTerraForged** | ✅ **单一解析水面** | **唯一正例**。三个关键手法（见下）。 |

### FTG 的三个关键手法（逐条对应我们的失败）

1. **水面是"定义的函数"，不是"解出的方程"**
   `waterHeight = fixedCurvedStep(大陆性)` —— 15 段台阶+smoothstep 的解析单值函数。
   处处单值 ⇒ **结构上不可能有两套水面打架**。全部下游（雕刻/地表/湿地/侵蚀/gasket）用同一份公式。
   对照我们：两个"解"（minimax + 水量平衡）必然打架——解与解之间没有一致性保证。

2. **湖不是水体对象，是"河流脊线的一段加宽"**
   `TerrainType.LAKE` 根本没注册（TerrainType.java:12-32 全部注册项无 LAKE）。
   湖 = `zone1Radius *= lakeMultiplier`，同一脊线、同一距离场，两端 smoothstep 平滑回 1.0。
   ⇒ **"水从湖里流出来"是构造保证的**：脊线本身就是内陆→海岸的连续线段（SimpleRiverGenerator:21-44）。

3. **湖内流向来自脊线方向，不来自水面求解**
   `storeFlowDirection`（UpliftRiverCarver:200-253）：
   ```
   flowDir = 脊线下游单位向量(dsX,dsZ)            ← 主项，|ds|=1 恒非零
           + 向心项 × turnWeight(≤0.35) × lakeDampening(=1/max(1,湖宽倍率))
   ```
   湖越宽 → lakeDampening 越小 → 越不往中心拉 ⇒ **直接消灭我们 85% lakeStill 的病**。
   该方向场与水面求解**完全解耦**（水面只管"淹到哪"，方向只管"往哪流"）。

## 三、我们的方案（折中：保留地形驱动，借鉴 FTG 三手法）

**不能整搬 FTG**（它的水面只依赖大陆性，无法表达"地形洼地积水成湖"——
我们的湖由地形决定，`flowaccum` 已有门禁）。折中如下：

### 3.1 核心改动：湖水位并入 1D 纵剖面（手法 1+2 的合体）

现状：湖水位 = 盆地内 2D 求解（两套水面打架的来源）。
改为：**湖水位 = 沿排水路径的 1D 纵剖面在"出口格"处的高程**：
- 湖段水面恒定 = 出口格高程（水平湖面，物理正确）
- 剖面在出口之后**继续下降**（下游真实地形）
- ⇒ "溢口外那格"就是剖面上的下一格，**不再存在"它是否干燥"的判断**
  （FTG 的 `waterY > scaledY` 判据在 1D 剖面下天然成立）
- 湖深仍由水量平衡决定湖面**低于**出口格的情形（枯水）；满水时湖面=出口格高程

### 3.2 湖内流向：沿脊线（手法 3 照抄）

湖内（以及全河道）流线的方向场改为：
```
v = 河道下游单位向量 + 向心项 × 0.35 / max(1, 湖宽倍率)
```
**湖内不再读 parent、不再读水面梯度** ⇒ parent 断裂与我们无关。
速度恒非零 ⇒ 无 lakeStill、无停滞。

### 3.3 EquilibriumWater 降级（保留但不当水面用）

- 保留：**盆地识别**（哪些格属于同一洼地）——这是它的强项，纯几何、无歧义
- 废弃：它的 `level` **不再作为最终水面**（只作候选集边界）
- 最终水面全部来自 3.1 的 1D 剖面

### 3.4 明确不做的事

- ❌ 不再把水位钳在鞍口 -1e-9（删除该语义，改为 3.1）
- ❌ 不再合并两套 2D 水面（第五修已证明此路不通）
- ❌ 湖内不再做任何 2D 求解

## 四、六阶段在新方案下的对应

| 阶段 | 实现方式 | 现状 vs 新方案 |
|---|---|---|
| 源头 | 河道格入度=0（不变） | 已有 |

## 五、风险与代价（如实）

1. **这是重写级改动**：`LakeWaterBalance` 核心语义、`ContinuousRiverNetwork` 的
   湖内流向、`HydrologyPipeline` 的数据流都要动。不是补丁。
2. **产出会变**：所有湖的水位/面积/河网形态都会变——已标定参数作废。
3. **A 线生产代码不受影响**（本方案只在 `model/` 诊断链内实施，
   验证通过后才谈接线——与用户此前"先在 worktree 验证"的决定一致，
   现在改为"先在 model/ 链验证"）。
4. **参考反证的警示**：SimpleHydrology 删除了同类洪泛；若本方案实施中
   发现 1D 剖面仍不能自洽，应停下重评估，而不是继续打补丁。

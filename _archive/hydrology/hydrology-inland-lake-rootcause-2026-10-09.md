# 「游戏里湖没了」根因定案：内陆 region 的 `resolved` 全域失效（2026-10-09）

> 用户判据：「模型链水文不就等于白做？为什么明明我要求渲染出图必须和游戏实机一样，
> 结果差这么多？」
> 用户选的方案：**B（湖水位局部化，照四个参考项目）**

## 一、★ 根因（实测锁定，一行代码）

`EquilibriumWater.compute` 第 77 行：

```java
boolean same = anyTrueDrain && Double.isFinite(levelA[k]) && ...;
//             ^^^^^^^^^^^^^^ 窗口内无海 ⇒ 这里恒 false ⇒ resolved 全 false
resolved[k] = same;
```

下游 `LakeWaterBalance` 第 262 行：

```java
isLakePot[k] = !sea[k] && resolved[k] && equilibrium[k] - bed[k] > 1e-6;
//                       ^^^^^^^^^^^ resolved=false ⇒ 一格湖都建不起来
```

### 实测证据（游戏配置 REGION=512/step=4，7 个 region）

| region | resolved | basins | lake | 说明 |
|---|---|---|---|---|
| (0,-1) | **0/31329** | 0 | **0** | 纯内陆（窗口无海）|
| (-2,-1) | **0/31329** | 0 | **0** | 纯内陆 |
| (-1,-2) | **0/31329** | 0 | **0** | 纯内陆 |
| (-2,0) | **0/31329** | 0 | **0** | 纯内陆 |
| (0,0) | 31199/31329 | 1 | 2 | 含海 ⇒ 正常 |
| (1,-1) | 29919/31329 | 12 | 84 | 含海 |
| (0,-2) | 28394/31329 | **46** | **376** | 含海 |

**⇒ 7 个 region 里 4 个因"窗口内没有海"而全区域失效** ⇒ 这就是用户看到
"渲染图有湖、游戏里没有"的直接机理。

### 为什么正典图从未暴露

正典探针用 **单窗口 r=700** —— 一个窗口跨越海岸线 ⇒ **总能找到海** ⇒
`anyTrueDrain=true` ⇒ 从不触发。而生产的 region 窗口（r=352）常常纯内陆。

**⇒ 这不是"参数没调好"，是 `EquilibriumWater` 的设计前提
（"种子必须是真实排水终端（海）"）在分块窗口下不成立。**

## 二、修复

**`EquilibriumWater.INLAND_RESOLVED`**（`-Dgeogenesis.inlandResolved=true`）：

无海窗口时，改用「B 组有有限水位」作为可信判据 —— B 组 =
真实地形 + `WindowOutlets` 的**真实窗外出口**（窗外一格的地形高）。
水位低于它时边界通量为零（水出不去，正确）；高于它则成为出口
⇒ **在本窗口内自洽且局部**，与 B 方案（局部量路线）一致。

### 效果（同 seed/中心/1401²）

| 配置 | 湖 | 河道 |
|---|---|---|
| 修复前（游戏配置）| **0.21%** | 2.72% |
| **修复后** | **7.38%** | 7.18% |
| 参照图（正典 r=700/step=1）| 3.63% | 1.96% |

`region (0,-1)` 的 basin 从 0 → **54**，lake 从 0 → **2699**。

### 附带实现的 B 方案第一步

**`LakeWaterBalance.LOCAL_LAKE_LEVEL`**（`-Dgeogenesis.localLakeLevel=true`）：
湖水位从「水量平衡 `solveLevel`（依赖全流域 inflow）」改为「溢出口高程 `sill`」。
实测影响很小（144872 vs 144760）⇒ 说明**水位公式不是主因，`resolved` 才是**。
保留该开关（与参考项目路线一致），默认 false。

## 四、剩余问题（如实）

1. **湖 7.38% vs 参照 3.63%（多一倍）** —— 可能 `INLAND_RESOLVED` 让过多格可信，
   或 `sill` 满湖语义使湖偏大。**需要 A/B 定量**。
2. **河道 7.18% vs 参照 1.96%** —— 掩码口径差（距离场 vs 流量阈值），未修。
3. **★★ R1 未修**：预览仍未走 provider（用户核心要求"渲染图 = 游戏"）。
   本次全部验证用的是 `ProductionViewProbe`（走 provider）⇒ 已比之前可靠，
   但 `CanonicalViewProbe`（真正的正典探针）仍是单窗口老路。
4. 适配层保留率仍只有 21%（去重口径）—— `Math.round` 摊派 + 多 region 冲突，
   未细查。

# 平面 ⇄ 沙盘 统一方案

> 用户裁定（2026-11-11）：
> 「把平面模式完整的重新设计一遍以达成与沙盘模式的设计与代码层的高度统一，
> 并保证平面需要的高精度块级预览效果。」
> 「**统一相机与交互，保留两套绘制。** 本身我也没打算让你一种样式表现平面和沙盘，
> 可以 2 种样式的。比如沙盘还是沙盘样式、平面可以试试我新给参考的样式。
> 二者流畅自然动画切换。」

## 一、被证伪的路线（先记下来，避免后人重犯）

### 1.1 「统一成一套几何：纹理高度场 + 侧裙」

设想：把地形画成「M×M 四边形，顶面贴平面纹理，高度跳变处补侧裙」，
则 `pitch=0` 时共面 ⇒ 逐像素等于平面图。理论上两边都保精度。

**A/B 出图实测（`runHeightfieldLookProbe`，`build/hf/ab_pitch95.png`）：**

| | 现有柱子 | 纹理高度场 |
|---|---|---|
| 块面感 | 清晰棱面 | 被平滑掉，像橡皮泥 |
| 对比度 | 强 | 明显变灰变淡 |
| 水面 | 蓝色湖面正常 | **水面丢失** |
| 边缘 | 干净 | 陡坡阶梯锯齿 |

**结论：为了「统一」把两边都改成同一种几何，结果两边都不如原来。**
这不是调参能救的，是方向错了。

### 1.2 教训

「统一」不等于「同一套几何」。平面要的是**信息密度**（每格看清），
沙盘要的是**立体形态**（起伏可读）。强行用一种几何承担两种目的必然互相妥协。

⇒ 统一**相机、数据、交互**；**不统一绘制**。

### 1.3 保留的两条出图（供后人复核）

| 探针 | 作用 |
|---|---|
| `runCameraDatumProbe` | 验证「pitch=0 就是平面图」的几何前提（5 条判据） |
| `runHeightfieldLookProbe` | 纹理高度场 vs 柱子的 A/B 出图（`build/hf/`），证伪用 |

## 二、采用的架构

```
PreviewScene（唯一场景）
  ├─ Camera：pitch / yaw / scale / center      ← 平面与沙盘共用
  ├─ Data：  TerrainFieldData（唯一，cellCache 派生）
  ├─ Style： GeoPalette + 光照配置（唯一）
  └─ 两条绘制后端，各自保留现有质量：
       GroundBackend（平面）：现有纹理管线 —— 地图感 + 块级精度，一行未改
       PillarBackend（沙盘）：现有柱子   —— 块面感，一行未改
```

**模式概念消失**：只剩一个连续的 `pitch`（0 = 平面，0.95 = 沙盘）与
「用哪个后端」的选择。

### 2.1 已验证的几何前提（`runCameraDatumProbe`）

| # | 事实 |
|---|---|
| 1 | 我们的相机是斜投影（与 diorama `Projection` 同模型，参数为补角） |
| 2 | `pitch=0,yaw=0` 时地面模型 ±1 **正好投到视口** `(0,0)-(854,451)` |
| 3 | `pitch=0` 时 `r5=0.000000` ⇒ 柱高完全不进屏幕 y |
| 4 | `pitch=0.95` 时 `|r5|=0.813` ⇒ 柱高显著可见 |

⇒ 平面 = 相机正俯视的特例，切换 = 相机 pitch 从 0 抬到 0.95。

## 三、运镜过渡（已实现，v49）

`ViewTransition`（纯函数，零 MC 依赖）定义全部运镜量：

| 量 | 平面端 | 沙盘端 | 说明 |
|---|---|---|---|
| `pitch` | 0 | 0.95 | 运镜主轴 |
| `yaw` | 0 | 用户当前角 | 最短角路径；平面端必须为 0 才能与平面图逐像素对齐 |
| `scale` | `(w/2, h/2)` 各向异性 | `fillScale` 各向同性 | **分量**插值，两端精确对齐 |
| `pillarAlpha` | 0 | 1 | 柱顶是粗色块，不淡入会盖成马赛克 |
| `groundAlpha` | 1 | 0（末 25% 淡出） | 地面是地基，柱体长满后自然遮住 |
| `lightStrength` / `waterStrength` | 0 | 1 | 预留给后续「光照/水面渐变」 |

### 3.1 渲染顺序（同一帧）

1. **地面贴图**：`PoseStack` 施加 2×2 仿射矩阵 + 普通 `blit`
   （斜投影是仿射的：地面 `y=0` 时只是「旋转 + 纵向压缩」，不需要手写 UV 顶点）
2. **柱体**：`SandboxRasterizer.setCameraOverride(yaw, pitch)` 用同一个相机渲染

两者共用 pitch/yaw/scale ⇒ 观感是「地形跟着镜头一起转起来」，不是两张图交替。

### 3.2 为什么不用参考项目的 zoomBoost / 高度插值

- `zoomBoost`（0.84→1.0）：那是图片过渡时代用来补立体感的替代品；
  运镜已由真实 pitch 插值提供，故删除（`SandboxRasterizer` 中已移除）。
- `heightScale`（0.45→1）：柱高是**地形量**，切视图不该改变；
  「立起来」由相机 pitch 抬起本身产生。
- `zoom`/`widthScale` 插值：参考项目能插是因为它两张图同单位；
  我们平面是整数档 `scaleBlockPos`、沙盘是浮点 `zoom`，且用户裁定切视图不改缩放。

## 四、验收判据

`runViewTransitionProbe`（8 条，全部 PASS）：

```
[1] 时长 600~1200ms
[2] progress 边界夹紧 + 单调
[3] pitch 两端值与单调（切沙盘抬升、切平面反向）
[4] yaw 平面端恒 0、最短角路径、沙盘端回到用户角度
[5] scale 两端精确对齐（平面端 w/2,h/2；沙盘端 fillScale）
[6] 柱体 alpha 平面端 0、沙盘端 1
[7] 地面 alpha 前 75% 保持 1、末段降到 0
[8] 无 NaN / 越界输入被夹紧
```

## 六、风险

| 风险 | 对策 |
|---|---|
| `PoseStack` 仿射 blit 实机表现（旋转/压缩是否生效） | 未实机验证；若失效会退化为"地面不跟随"，需实机确认 |
| 平面模式回归 | 稳态平面仍走原 `blitPlaneOnly`，运镜只在过渡期生效 |
| 柱体与地面在过渡中大小不一致 | 两者都用 `SandboxRasterizer.drawScaleFor()` 的同一个 scale |
